# AI 任务编排

适用于不简单的编程、调试、跨文件探索、多源调研、运营、营销、数据和长期任务。简单回答、小改动和线性任务直接做，不需要这套。

## 先判断：要不要拆

对每个不简单的任务，先粗略看有没有这样的子任务：

- 能独立或并行完成；
- 能把大量日志、原始资料、测试输出或代码探索隔离在主线程之外；
- 能提供一条真正不同的证据线或反方审查；
- 能试一个替代方案，又不和别人写同一批文件。

如果有至少两个可以分别交付、分别验收、读写范围清楚、互相没有未解决依赖的工作包，默认就并行跑最小的一组（通常一到两个子任务），主线程同时推进自己的那一份。

需要串行的情况：上游依赖未解决、只有一个共享的图形界面、会写同一批文件、没有空闲执行资源。这时写下具体卡在哪、什么条件下解除。“协调成本高”这种笼统理由不能无限期地拒绝并行。

不要为了凑数量发明工作包。

## 任务包写什么

每个子任务的任务包包含：

- 目标和交付物；
- 唯一的工作范围（读哪些、写哪些）；
- 前置条件、来源和证据位置；
- 共享资源归谁；
- 检查方法和停止条件；
- 谁负责整合和最终验收。

子任务是“叶子”：不再继续往下拆，完成后返回实际产物位置、覆盖范围、验证结果和遗漏。

## 上下文

- 给最小的足够上下文：优先“完整任务包 + 不继承聊天历史”；确实需要最近对话时只带几轮。
- 不让两个执行者同时写同一批文件：按归属拆开，或者改成串行。
- 用完成事件或长等待，不要频繁轮询状态。

## 运行中重新评估

工具、用户或验证结果改变了对目标、事实、授权、依赖、方法或风险的理解时，只重评受影响的部分，保留仍然有效的成果。换方法必须带来明确收益；同一工作包始终一个负责人、一条活动路线。

## 证据循环

成功能被客观检查时：

1. 定义成功、证据、停止条件、升级条件和花费上限。
2. 做最小的完整尝试。
3. 用测试、构建、浏览器行为、对账、来源覆盖或成品检查来验证。
4. 按证据修正，再验证。

失败或结果不确定时：先分类并核对实际结果；对已授权、可重试的工作，在风险和预算范围内至少做三次有意义的不同尝试。权限被拒、副作用不确定、永久错误、需要输入、额度用完，按各自的停止条件处理。重复失败要换诊断思路，而不是重复同样的动作。

主观的工作，写清评审标准和不确定性，不宣称无法衡量的“客观通过”。

## 独立复核

- 简单任务没有明显收益时可以跳过。
- 高风险的配置、架构、智能体或工作流系统，或者同一类问题反复失败时，安排一次只读的独立复核。
- 复核者看真实的交付物和执行证据：改动的文件、测试结果、截图、措辞、遗漏和风险；返回分级的发现，不替主线程做决定，也不再派生子任务。
- 默认一轮。主线程逐条评估发现，修掉有效问题，对 P0／P1 做一次针对性复验。不要搞“复核—修—再复核”的自动循环。

## 预算与验收

- 证据已经足够时，停掉重复或不再需要的工作线。
- 真实用户的社区证据和品牌／厂商说法分开放。
- 最终验收归主线程：亲自看关键成品和验证证据，不信任子任务的自我报告。
- 运行时的限制如实报告：已生效、部分生效或推迟。光有指令和配置不等于行为已验证。

## 常见形态

- 调研：官方证据 + 社区证据 + 竞品证据 → 综合 → 反方审查 → 主线程决定。
- 编程：代码结构梳理 + 当前文档 + 复现 → 实现 → 测试或浏览器验证 → 复核 → 主线程验收。
- 运营：来源核对 + 数据准备 → 执行 → 对账 → 恢复或完成。

## 边界

拆分任务不会带来任何额外授权：对外写入、破坏性操作、生产环境修改、购买、登录或发布，仍按原来的授权。配置和日志只做有针对性的脱敏读取，凭据通过安全入口使用。
